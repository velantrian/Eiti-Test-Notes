# Эскиз офлайн-движка EITI

**Коротко:** второй ИИ-сервис не нужен. Практичнее усилить уже имеющуюся локальную цепочку: распознать речевое намерение, найти карточку на устройстве, ответить только при достаточном совпадении, иначе честно уточнить или сообщить о пробеле. Этот эскиз основан на рабочем дереве Draft PR #59; это проектное предложение, не изменение кода.

## Что уже есть

В библиотеке — **545 карточек понятий в 20 доменных пакетах**; проверенный несжатый размер их поисковых индексов и самих карточек — примерно **408 КБ**. Общий KB-индекс содержит 31 541 запись. Пакеты загружаются лениво, а Service Worker кладёт файл в офлайн-кэш при первом запросе; поэтому понятие, которое устройство ещё не загружало, не обязательно будет доступно без сети.

Текущий формат карточки уже удобен как основа: `q` — названия и поисковые триггеры, `a` — основное определение, необязательное `en` — английский текст, `f` — дополнительные поля (`short`, `ex`, `why`, `how`, `use`, `when` и др.), `r` — связанные карточки. Сверху пакета уже есть `v`, `domain`, `part`, `entries`; ID — ключ записи в `entries`.

В `EitiFrames` есть правила для вопросительных форм, выбора, тем, эллипсиса и follow-up; состояние хранит активную карточку и уже рассказанные поля. Но результат парсера не является вероятностью: поле `n` — длина найденного триггера. Текущий KB-движок использует BM25-подобный поиск и отдельные отсекающие правила, а не единый калиброванный score.

Приоритет цепочки в текущем приложении: **Care (кризис/поддержка) → нормализация и контекст диалога → локальные действия и личные данные → Frames → KB-карточки → офлайн-диалоги/сказки → честный ответ «не нашёл»**. Care стоит перед нечётким разбором. Неизвестные темы журналируются локально; обновление базы и получение коротких карточек Википедии выполняются только через явное действие в настройках.

## Предлагаемый поток

```text
сообщение
  → Care и безопасные исключения
  → нормализация текста + контекст диалога
  → локальный калькулятор / запрос к заметкам и файлам
  → Frames: намерение + тема + ссылка на предыдущую карточку
  → поиск подходящей локальной карточки
  → проверка уверенности, языка, свежести и наличия нужного поля
  → ответ по карточке либо уточнение / диалоги / честный пропуск
```

Не переставлять личные данные выше защитного слоя и не отправлять запрос в сеть «на всякий случай». Офлайн-цепочка должна завершаться локально; онлайн-поиск или ИИ — отдельный выбор пользователя.

## Формат карточки

Сохранить текущие поля `q/a/en/f/r`, не ломая существующие пакеты; добавить необязательные метаданные происхождения и актуальности. Пример расширения, **предлагаемая часть отмечена `meta`**:

```json
{
  "v": 2,
  "domain": "kn_biology",
  "part": 0,
  "entries": {
    "kbl_kn_biology_example": {
      "q": ["фотосинтез", "процесс фотосинтеза"],
      "a": "Фотосинтез — процесс, при котором...",
      "en": "Photosynthesis is the process by which...",
      "f": {
        "short": "Растение использует свет, чтобы запасать энергию.",
        "how": "...",
        "why": "...",
        "ex": "..."
      },
      "r": ["related-card-id"],
      "meta": {
        "schema": "eiti.card.v1",
        "sources": [{"field": "a", "type": "curated", "url": "https://…"}],
        "reviewed_at": "YYYY-MM-DD",
        "freshness": "stable"
      }
    }
  }
}
```

`freshness`: `stable` для базовых понятий, `periodic` для меняющихся сведений, `live` для данных, которые нельзя обещать как актуальные в офлайне. Для `periodic/live` показывать дату проверки; после истечения срока не выдавать карточку как свежий факт. Источник и тип записи (`curated`, `Wikidata` и т. п.) должны описывать происхождение, а не гарантировать истинность.

## Уверенность: текущие правила и стартовые пороги

**Что уже действует в коде:** обычный прямой ответ KB проходит проверку `cov ≥ 0.60` и `prec ≥ 0.50`, плюс дополнительные ограничения на короткие, сгенерированные и омонимичные совпадения. Карточка понятия требует `nx > 0`, `cov ≥ 0.60`, `prec ≥ 0.75`, отсутствия омонимии и достаточного score относительно верхнего результата. Это правила допуска, а не проценты вероятности. Frames пока не считает числовую уверенность.

**Что предлагается добавить:** отдельный `confidence` в диапазоне 0–1, рассчитанный по точности намерения, совпадению темы/алиаса, разнице между первым и вторым результатами и надёжности контекста. Опечатка или транслитерация снижает уверенность; контекст помогает только если ссылка ведёт на однозначно активную карточку.

- **`≥ 0.85` — ответить**, только если прошли жёсткие KB-гейты, нет омонимии, есть заметный отрыв от второго кандидата (стартовая проверка: `top1 ≥ 1.25 × top2`) и в карточке есть запрошенное поле.
- **`0.60–0.84` — уточнить**, например показать два понятия на выбор; не выдавать один из них как установленный факт.
- **`< 0.60` — не угадывать**: перефразировать вопрос, предложить заметки/локальный поиск или честно сообщить, что ответа нет.

Эти числа — **гипотеза для испытаний, не текущая функциональность и не измеренная точность**. Перед выпуском пороги следует откалибровать на отложенных позитивных и отрицательных примерах; отдельно посчитать ложные уверенные ответы. Кризисная маршрутизация остаётся отдельным жёстким правилом и никогда не зависит от этого score.

## Если сведений не хватает или устройство офлайн

Различать три ситуации: **карточки нет в базе**, **карточка есть, но её пакет не скачан**, **поле карточки отсутствует**. Сейчас все они могут выглядеть для пользователя похоже; интерфейсу полезно объяснять причину.

- Если тема двусмысленна — задать один короткий вопрос. Если нет карточки — сказать «в локальной базе не нашёл», не сочинять определение; записать тему только локально и предложить поискать в заметках.
- Если пакет не кеширован — сказать «этот пакет ещё не скачан на устройство». Не утверждать, что такой карточки вообще нет. Когда появится сеть, предложить кнопку обновления.
- Если поле отсутствует — честно сказать, что в карточке нет именно этой детали; предложить доступное поле или поиск после подключения.
- Без сети не запускать Wikipedia, удалённый API или модель. Уже закешированные карточки, заметки и офлайн-диалоги работают; незагруженные материалы недоступны. Не обещать, что офлайн-ответ проверен на свежесть.
- В стандартный набор разумно включить все 545 карточек понятий: их текущий сырой объём около 0.4 МБ. Полный индекс из 31 541 записи оставить ленивым или сделать отдельной загрузкой. Показывать статус вроде «карточки понятий: 545/545 на устройстве».
- Обновлять пакеты по явной кнопке: скачать изменившиеся файлы, сверить SHA-256, проверить структуру и лишь затем переключать кэш. При ошибке сохранить прежний рабочий набор. Не отправлять журнал неизвестных тем автоматически.

Для языка ответа сохранять тот же принцип: если у карточки нет текста на запрошенном языке, не делать вид, что это локальный перевод; сообщить о доступном языке или пропустить карточку в существующий локальный слой.

## Минимум проверок перед реализацией

1. Unit: карточка валидна/повреждена; нужное поле есть/отсутствует; точный алиас, опечатка, омоним и почти равные top-2; follow-up с актуальным, устаревшим и пустым контекстом.
2. Offline E2E: после предзагрузки карточка отвечает при отключённой сети и не делает сетевых запросов; незагруженный пакет даёт отдельное честное сообщение; ошибка SHA-256 не стирает прежний кэш.
3. Языки: RU/EN/DE проверяются отдельно; отсутствие перевода не подменяется случайным ответом.
4. Метрики на holdout: отдельно intent accuracy, правильность темы, доля уточнений и **ложные уверенные ответы**. Порог выбирается по тестам, а не по удобству демо.

## Где это видно в текущем дереве

`local/eiti_frames.js` — парсер, контекст, ответ и follow-up; `local/eiti_care.js` — защитный слой; `kb/eiti_kb.js` — скоринг и `confident()`; `index.html:32437–32585` — ленивая загрузка/поиск KB, `32867–32960` — Frames, `32962–33160` — журнал пропусков и обновление пакетов, `33191–33502` — локальные wrapper-слои; `kb/index.json`, `kb/idx/kn_*.json`, `kb/packs/kb_kn_*.json` — данные карточек; `sw.js` и `offline_manifest.json` — кэш и манифест.
